# Research: Model Picker Compatibility

**Feature**: [spec.md](./spec.md)  
**Target**: VS Code 1.146

## Decision 1: Treat model picker configuration as request-level input configuration

- **Decision**: Keep the context-size preference model-specific and consume the selected `contextSize` from the VS Code request's model configuration. Compute the request's effective input budget from the selected total context and the model's output-token reservation. Maintain separate behavior for models requiring the optional 1M-context opt-in.
- **Rationale**: The repository's generated provider API contract states that values in a model's `configurationSchema` return in request `modelConfiguration`; the provider already consumes these values and adjusts local context budget/1M headers. The agreed requirement is an effective per-model maximum input context, not only display metadata. Existing schema exposes context selection where a local cap or optional 1M choice is meaningful.
- **Alternatives considered**: Persisting a global setting (would make a model-local picker choice affect unrelated requests); changing only the advertised `maxInputTokens` (does not enforce the actual request limit); removing picker configuration (contradicts the requirement).
- **Evidence**: `src/vscode.d.ts` `LanguageModelConfigurationSchema` and `LanguageModelChatRequestHandleOptions.modelConfiguration`; `src/provider.ts` `buildConfigurationSchema` and `provideLanguageModelChatResponse`.

## Decision 2: Treat provider metadata as a per-surface UI contract, not a generic rendered tooltip

- **Decision**: Audit all fields emitted for each model in VS Code 1.146 against the separate picker and Manage Models/Add Models consumers. Keep owner, retention warning, prices, context, and capabilities in the fields consumed by each surface; use concise plain text in the Manage Models hover and Markdown only for surfaces that render it. Newline preservation in the model-name hover is controlled by VS Code, not provider metadata.
- **Rationale**: `LanguageModelChatInformation.tooltip` is a string, and the inspected 1.146 Manage Models name hover escapes provider tooltip text and gates it behind a status icon. the expanded picker Details surface and Add Models table have different metadata handling. Numeric `*Cost` fields are interpreted as Copilot credits in the Details view and hovers. Preserve the existing formatted AWS USD strings in `*Cost` for the Add Models table; as requested, accept that picker Details may display these non-numeric strings as Unknown, and do not label them as Copilot credits.
- **Alternatives considered**: Putting all content in `tooltip` (raw markdown is escaped in the table and the tooltip is omitted on some entries); duplicating all metadata into `detail` (too dense and does not supply structured warning/cost data); replacing the working table cost strings (unnecessary regression).
- **Evidence**: `docs/VSCODE_INTEGRATION.md`, `src/provider.ts` model-information construction and metadata type, and installed local VS Code 1.146 source. Live Add Models visual verification still needs a model exposed in an interactive session.

## Decision 3: Determine the model identity that owns the open Details card

- **Decision**: A provider-emitted schema can only drive the card for a model whose metadata retains that schema. VS Code 1.146 supports the direct Bedrock model's `tokens`-group `contextSize` enum, but the user's ordinary Chat-with-Copilot window may be hosted by the `agent-host-copilotcli` session target when the computed/remembered default session provider selects it. In that case its picker selects a separate agent-host-owned mirror of the Bedrock model, constructed from a reduced BYOK DTO with no context-size schema or request configuration field. The visible Chat window/model name does not reveal that internal target; inspect model-selection diagnostics.
- **Rationale**: The provider trace proves that direct `bedrock/global.openai.gpt-6-luna` metadata contains valid `[256K, 750K, 1.05M]` context options. The user's latest selection and request evidence identify the visible Chat window's Bedrock request, but the available renderer log for that window is from an earlier run and cannot establish which internal model identity backed the screenshot's card. In that earlier run, the ordinary workbench panel restored a remembered `agent-host-copilotcli:bedrock/global.openai.gpt-6-luna` selection; the general model list also contained the direct `bedrock/...` entry. These identities route to the same Bedrock model name, so the response label does not distinguish them. VS Code 1.146's `AgentHostByokLmHandler.listModels` exports only context maxima/reasoning properties, `CopilotAgent._refreshByokModels` synthesizes only a thinking-level config schema, and `AgentHostLanguageModelProvider` maps that reduced schema to picker metadata. The agent-host copy lacks `contextSize`; its Details card therefore displays static Max context. The direct provider schema does not fix that second identity, and its request bridge also lacks a context-size field. To diagnose the user's current direct-Chat card conclusively, capture that card-open event's model identifier and runtime schema; do not treat a prior session restore as proof of the current screenshot path.
- **Alternatives considered**: Keep changing `buildConfigurationSchema` on the direct provider (already proven to emit the right values); infer controls from `maxContextWindowTokens` alone (the card renders that as static Max context); expose only an agent-host context enum (selection would not reach the Bedrock provider and would imply a working control that has no effect).
- **Evidence**: `internal_docs/vscode_copilot_context.md`; VS Code 1.146 source for `agentHostByokLmHandler.ts` (`listModels`/`chat`), `copilotAgent.ts` (`_refreshByokModels`), `agentHostLanguageModelProvider.ts` (`_toLanguageModelConfigurationSchema`), `agentHostByokLm.ts` DTO definitions, `modelPickerCard.ts`, and the ordinary-panel renderer log. The remaining limitation is in VS Code/Copilot-owned bridge code, not the direct provider.

## Decision 4: Use the existing project structure and mock-based provider tests

- **Decision**: Keep implementation within the current provider/profile modules, extend focused tests in `src/test/provider.test.ts`, and update `docs/VSCODE_INTEGRATION.md`. Use the existing VS Code test installations, including 1.146, for target-runtime validation.
- **Rationale**: The behavior is an extension-provider/API compatibility issue; upstream layout is not modifiable, and existing provider tests cover schema construction, cost formatting, retention metadata, and token-limit helpers.
- **Alternatives considered**: Adding a separate UI/plugin layer or AWS integration path (unnecessary architecture and operational side effects); only documenting behavior (does not restore UI/request functionality).

## Decision 4: Compact oversized history with a request-local Bedrock summary

- **Decision**: Estimate converted message and system content against the selected effective input budget. If history exceeds it, summarize older conversation through the selected Bedrock model, preserve the current turn and latest complete tool interaction, and reject the request if safe compaction cannot fit. Skip summarization when history fits; do not persist or log transcripts or summaries.
- **Rationale**: Enforcing the selected context setting requires an explicit policy for histories already larger than the chosen limit. Summarizing older turns retains useful context without silently dropping it, while preserving recent user intent and tool exchanges.
- **Alternatives considered**: Send an oversized request (does not honor the setting); truncate or discard prior turns silently (risks losing relevant context); reject every over-limit request (avoids an added call but provides poorer continuity).
- **Evidence**: `src/context-compactor.ts`, `src/provider.ts`, `src/bedrock-client.ts`, and focused mock-based tests in `src/test/provider.test.ts`.
